# M5-07 批量、双模式与完整轨迹联调验收

## 验收入口

仓库根目录执行：

```powershell
pwsh -NoProfile -File code/scripts/verify_issue_035.ps1
```

该入口运行前端共享任务行为测试、类型检查和生产构建，然后创建随机 Compose 项目、独立数据库及附件卷。它应用 Alembic 迁移并检查模型一致性，执行相关审批、幂等、额度、批次、恢复、轨迹、脱敏和审计回归，再启动隔离 Worker，调用本机配置的 DeepSeek 与真实 MCP。

在线联调覆盖：

- 混合 Excel 批次包含一笔有效订单、一个超额组和一个缺字段组；只有有效组创建持久子任务，重放幂等键不会创建第二个批次。
- 有效组由 Worker 使用真实模型和 MCP 工具处理，在人工审批处等待；超额和缺字段组不能被批准，也不能创建订单或占用额度。
- 等待补充任务及批次的审批等待各重启一次隔离 Worker；任务 ID、等待状态、checkpoint 和 interrupt 回查保持不变。
- 由另一名授权审批人批准当前草稿版本，核对批次结果、订单详情、审批人、版本摘要、额度占用、任务事件和审计记录。
- 前端已有的悬浮窗/全屏共享 Pinia 行为回归验证同一任务、单事件连接、编辑缓冲、未发送内容、重复事件和补充提交；切换模式不触发新任务或工具调用。

后端回归使用同一轮隔离数据库。启动在线 Worker 前，验收脚本会将回归测试遗留的 `READY`/`RUNNING` 作业及仍处于排队/执行状态的关联任务标记为隔离失败，并按本轮容器环境重建当前运行配置快照，避免测试样本占满并发额度或将旧配置（例如错误的 MCP 端口）带入真实联调；这些操作只作用于随机 Compose 项目数据库。

`-OfflineOnly` 可快速执行离线及隔离 API/数据库回归，但会明确报告没有运行在线模型联调，不满足本 issue 的完整关闭条件。

## 隔离与清理

- `.env` 的 DeepSeek 密钥只经 Compose 环境注入，不打印、不写入测试产物或仓库。
- 验收使用随机 Compose 项目名、随机端口、独立数据库和附件卷，演示密码及 MCP/运行配置加密密钥每轮随机生成。
- 成功或失败时仅执行该随机项目的 `docker compose down --volumes --remove-orphans`，不停止、重启或清理默认 `code-*` 开发容器。
- 正式订单只写入本轮隔离数据库，关闭项目时一并清除。测试不会访问或修改默认开发数据库。

## 结果解释

- 离线 pytest 与隔离 API/数据库测试验证规则、事务和持久状态，不等于模型已在线工作。
- `LIVE` 模型 span 与成功 MCP 工具 span 才作为本轮真实在线模型/工具证据；缺少 Token usage 时仍标记不可用，不填造 Token 数。
- 真实审批和订单以订单、TaskApproval、QuotaOccupation、TaskEvent 及 AuditEvent 的数据库记录交叉核验。
- 线上订单 ERP 对接与生产环境容量/长稳指标不在本 issue 范围；分别由后续里程碑或部署验收处理。
