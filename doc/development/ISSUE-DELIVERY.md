# 持续开发与 Issue 交付流程

本文定义 TradePilot 按依赖推进既有实现 issue 时应长期遵守的流程。PRD、Spec 和原型定义产品与技术要求；GitHub issue 记录单项实施进度和证据；本文只记录稳定流程，不保存 issue 正文或临时进度。

## 1. 每轮开始与状态恢复

1. 阅读仓库根目录及目标目录中的 `AGENTS.md`，确认仓库根目录、远程地址、默认分支、当前分支、工作区状态和最近提交。
2. 从 GitHub 重新读取目标范围的 issue、PR、分支和提交。旧对话或本地记忆不能替代远端事实。
3. 优先续做已有未完成开发分支或 PR。否则按 M1 至 M6 顺序选择前置依赖已实际交付的 issue；关闭状态本身不能证明依赖已完成，须核实其合并变更和所需接口、能力或验证证据。
4. 同一阶段中优先级较高者先做；条件相同按规划标识和 issue 编号排序。出现循环依赖、文档冲突或关闭但没有交付的依赖时，记录事实并先解决；如仍有其他满足条件的事项，可继续推进。
5. 开始前确认未有相关实现、分支或 PR，读取 issue、PRD、Spec、原型和依赖交付。保留用户改动，不覆盖、不擅自暂存或清理。

选定后记录本轮变量：`ISSUE_NUMBER`（实际编号）、`ISSUE_KEY`（如 M2-06）、`ISSUE_SLUG`（简短英文分支主题）、`DEFAULT_BRANCH`（仓库实际默认分支）。分支、提交、PR 和验证文件使用实际变量，不把示例编号写死。

## 2. 范围与实施

- 每轮只交付一个 issue 的范围。先说明范围、关联的六项核心能力、预期交付程度、阶段提交划分和验证入口。
- 以 issue 验收条件及 PRD、Spec、原型和前置交付为准。发现的范围内缺陷在本轮修复；P2 或无关需求记录为后续事项，不静默扩大范围。
- 六项核心能力按 issue 和里程碑逐步交付，不要求单个 issue 实现全部能力。已声明交付的能力必须有可执行实现与可复查证据；依赖安装、界面展示和静态示例不算能力交付。
- 注释解释模块职责、关键设计原因、业务约束、状态变化、事务边界和失败恢复；不逐行翻译代码，也不留下过时或相互矛盾的说明。重要技术选择记录在实现说明并关联提交。
- 普通实现选择自行依据仓库资料解决。只有影响业务规则、公共契约或范围且无法从现有资料查明的实质问题才请求澄清。

## 3. 分支与阶段提交

- issue 分支命名为 `codex/issue-{ISSUE_NUMBER}-{ISSUE_SLUG}`，从实际默认分支或已确认的续作分支开始。
- 分阶段提交，每个提交都是独立、可解释、尽量可运行的成果；功能提交包含对应测试和必要说明。不 squash 或重写已形成的阶段提交，不强推共享分支。
- 提交标题使用中文方括号前缀：`[新增]`、`[更新]`、`[修复]`、`[重构]`、`[测试]` 或 `[文档]`。正文说明完成内容、主要设计原因、该阶段验证方式和实际结果，并写 `Refs #实际编号`。
- 提交前检查完整暂存范围，排除无关改动、凭据、临时文件及生成产物。未确认属于本任务的改动予以保留。

## 4. 稳定验证入口

每个实现 issue 提供：

```text
code/tests/issues/test_issue_NNN.py
```

`NNN` 为三位实际 issue 编号。跨前端、后端或 Compose 编排时，可增加：

```text
code/scripts/verify_issue_NNN.ps1
```

验证入口必须运行实际检查，包含有效断言，失败时返回非零退出码；不得只打印成功。按模块组织测试并复用已有公共能力，不复制业务逻辑。覆盖正常、边界和失败路径，并说明：

- 环境、依赖准备和执行命令；
- 验证内容、预期结果和失败排查；
- Docker、数据库、网络和凭据要求；
- 数据副作用及安全清理方法。

结果分为本地/离线验证、真实服务集成验证、在线模型评测。测试替身只用于明确标注的开发和离线测试，不能作为真实集成证据。缺少必要环境时写明未验证原因，不把跳过、未执行或示例输出记作通过。默认测试使用隔离示例数据，不操作真实业务数据，不执行全局破坏性清理。

## 5. 审查与修复

提交 PR 前审查相对目标分支的完整差异，核对：

- issue、设计和验收要求是否全部覆盖，且没有提前实现其他 issue；
- 模块边界、接口兼容、权限、事务、并发和幂等约束；
- 异常处理、日志脱敏、敏感信息、配置与运行说明；
- 测试断言及关键失败路径，注释与实现是否一致；
- 六项能力相关模块是否退化，示例或模拟是否被误称为真实服务结果。

发现问题时记录文件与行号、触发场景、影响、严重程度、证据及修复建议。阻塞项和违反验收的问题须修复，相关验证通过后复审。自审应如实标记为自审，不称为独立人工审批；风格偏好不作为无边界重构理由。

## 6. PR、合并与清理

本地必要验证和审查通过后，推送 issue 分支并创建 PR。PR 标题使用中文方括号格式；正文至少说明背景与关联 issue、实施范围和设计、阶段提交导读、验收及实际证据、测试命令和通过/失败/跳过/未执行状态、配置/迁移/运行变化、限制与回退方式，并使用 `Closes #实际编号`。

创建后核实 PR 实际差异和提交集合、必要检查与审查意见、冲突状态，以及源分支 SHA 是否仍与已审查和验证的 SHA 一致。源分支变化后重跑受影响验证；目标分支变化影响结论时更新并重新验证。不得关闭必要 CI 或绕过分支保护。必要验证、审查和仓库规则均满足后，使用 merge commit 合并并保留阶段提交。

合并后逐项确认：

1. PR 状态为 `MERGED` 并记录 merge commit；
2. issue 已关闭，若未自动关闭，在核实交付完成后关闭；
3. 删除本轮已经合并的远程开发分支；
4. 安全切回本地默认分支，获取远端更新并 fast-forward；
5. 确认本地默认分支与 `origin/{DEFAULT_BRANCH}` 一致，再删除已确认合并的本地 issue 分支并清理其失效远程引用。

若存在冲突或未知改动，不用强制重置或强制删除规避。保留其他分支及用户数据。

## 7. 里程碑与持续目标

每个 issue 完成后，从 GitHub 重新读取状态并选择下一个满足依赖的目标范围 issue，不因完成一个 issue 就认为整个目标已完成。里程碑结束时，汇总六项核心能力的实际实现范围、验证证据和剩余事项。

每轮交付摘要记录 issue 与范围、阶段提交及关注点、测试结果、审查与修复、PR/issue/merge commit、分支及工作区状态。持续目标只有在全部范围内 issues 已真实合并关闭、必要验收有实际证据、没有未解决阻塞缺陷、本任务分支已安全清理且本地默认分支与远端一致时才算完成。
