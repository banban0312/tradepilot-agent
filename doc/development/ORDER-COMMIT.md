# 正式订单原子提交

## 提交边界

只有 Worker 恢复真实审批等待点，并确认人工批准仍绑定当前草稿版本和内容摘要后，才会调用 `commit_approved_order`。模型、MCP 工具和浏览器请求都不能直接调用正式订单提交服务。

提交事务按任务、草稿、批准、合同、合同金额额度账、按主键排序的合同物料额度账、订单编号计数器、任务事件游标的顺序取得锁。Worker 先锁定任务行并校验当前执行 epoch。金额和数量在这些锁保持期间重新核验；等于剩余额度时允许提交。

事务同时写正式订单、订单明细、额度占用流水、合同金额和数量聚合、草稿锁状态、任务完成状态、审批责任审计和任务事件。任一写入失败会回滚整笔订单及全部额度变化。

订单使用任务、批准快照和服务端提交键唯一约束。若数据库事务已提交而 LangGraph 检查点或 Worker 响应尚未完成，重放会查询并返回既有订单，不重复增加额度。额度账缺失或实时规则发生变化时不创建订单：旧批准失效，草稿恢复可编辑，任务进入 `BLOCKED_RULE` 输入等待，审计记录保留阻断原因。

订单编号格式为 `XSDD-客户代码片段-业务日期-序号`（销售）或 `CGDD-客户代码片段-业务日期-序号`（采购）。序号按方向、部门和业务日期在事务中串行分配。

## 验证

在 Windows PowerShell、Docker Desktop 已启动且 `code/backend/.env` 已配置的情况下，从仓库根目录执行：

```powershell
pwsh -NoProfile -File code/scripts/verify_issue_016.ps1
```

脚本创建随机命名的隔离 Compose 项目和 PostgreSQL 数据卷，使用 `uv` 执行迁移、ORM/迁移一致性检查、种子数据和测试。验收包含批准失效、审批权限撤销和不匹配批准快照回放均无订单/占额副作用；同一批准 20 次并发/重放只产生一张订单和一次占额；两笔各 100000 元竞争 150000 元时只允许一笔成功；精确用尽剩余额度可以提交；实时规则阻断会返回 `BLOCKED_RULE` 输入等待；并回归 #8、#13、#14、#15。

脚本退出时只清理它创建的随机 Compose 项目及数据卷，不会停止或清理用户已有项目。在线模型评测未执行；本验证不调用模型供应商。
