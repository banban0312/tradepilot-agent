# 物料纠错与证据采纳

工作台的“匹配标准物料”通过任务 API 查询真实主数据。服务端复用 M2-03 的 `match_materials` 查询逻辑，不从前端字典或固定示例生成候选。多个规格或缺少规格时会保留全部候选并要求人工选择，不自动采纳首项。

## 接口与业务边界

- `POST /api/v1/tasks/{task_id}/material-matches`：请求当前草稿版本和明细序号，返回数据库候选、规格、单位、匹配理由及确认提示。要求登录、CSRF、经办角色、部门权限和有效任务等待点。
- `POST /api/v1/tasks/{task_id}/material-decisions`：只接受 `REJECT`，并验证候选仍来自当前明细的匹配结果。写入包含用户、时间、版本、候选编码和输入摘要的追加式审计；不会改草稿或创建订单。
- 采纳经原有 `PATCH /api/v1/tasks/{task_id}/draft` 保存。服务端重新查询候选，验证所选主数据仍启用且规范规格、单位一致；保留原始物料名称，并将候选身份与规范值写入 `field_evidence`。当来源证据包含附件和定位时一并沿用，确认人由登录身份写入。内容变化生成新草稿版本并按既有事务规则使旧批准失效，任务恢复后重做业务校验。

候选查询供等待中的经办人交互使用，直接调用共享的主数据匹配领域服务；模型调用链仍通过真实 MCP `match_material` 工具和既有租约授权完成。该 UI 查询接口不伪装成 MCP 传输调用。

## 验证

在仓库根目录执行：

```powershell
pwsh -NoProfile -File code/scripts/verify_issue_025.ps1
```

脚本需要 Docker、`code/backend/.env`（依照 `.env.example` 设置本机数据库参数）以及 `uv` 锁文件所需的依赖镜像。它使用随机 Compose 项目、独立 PostgreSQL 和附件卷，清理范围限于本次随机项目；会将演示模式密码设为随机值，并将模型及外部 OCR 凭据覆盖为空。不会调用在线模型。

验收包含规格歧义候选不自动选择、跨部门访问拒绝、CSRF、候选过期/错误规格拒绝、采纳和拒绝审计、原词与页定位证据、真实确认人、草稿版本更新、旧批准失效及正式订单零新增，并回归物料查询、工作台、PDF 和图片解析。

前端类型检查与生产构建：

```powershell
cd code/frontend
npm run build
```

在线模型评测和 ERP 集成不是本 issue 的验收范围；图片 OCR/PDF 证据分别由前置 issue 的离线与服务端验证覆盖。
